Agent Sandbox Deep Dive

A walk through one request in the agent sandbox, then every term the design uses, layer by layer, with why each one matters here. The diagram lives at Agent Sandbox Architecture.

The design in one sentence. The agent runs on a different kernel from the host, has no network, and holds no secrets. Its only way out is one socket to one host process, and that process decides, adds credentials and records every request.

One request, end to end

The agent's GitHub tool wants to open an issue.

  1. The tool calls the proxy in plain HTTP. POST http://127.0.0.1:8080/github/repos/x/y/issues, with no Authorization header. The tool has no token, and the guest has none to give it.
  2. The request goes onto vsock. The guest has no network card, but vsock is its own socket family and doesn't need one. There are three ways onto it:
    • The tool opens AF_VSOCK itself and connects to CID 2 (the host), port 8080. Python's socket.AF_VSOCK, Go's mdlayher/vsock and Rust's tokio-vsock do this.
    • A Unix-socket shim: socat UNIX-LISTEN:/run/egress.sock,fork VSOCK-CONNECT:2:8080, then any client that speaks HTTP over a Unix socket (curl --unix-socket, httpx with uds=).
    • A loopback TCP shim: socat TCP-LISTEN:8080,bind=127.0.0.1,fork VSOCK-CONNECT:2:8080. Any HTTP client works unchanged, but it needs TCP/IP in the guest kernel, so only the default profile has it.
  3. The guest's virtio-vsock driver queues the bytes in a ring buffer in guest memory and notifies the device.
  4. KVM traps the notification and hands it to Firecracker. Firecracker's vsock device reads the ring. It sees a connection to port 8080 and connects to the host Unix socket <uds_path>_8080. Under the jailer that's something like /srv/jailer/firecracker/agent-01/root/v.sock_8080.
  5. Envoy is listening on that socket. The listener is bound to that one file, so Envoy knows the caller is agent-01 without asking the guest anything.
  6. Envoy's router matches the route. /github/ maps to the github cluster. A path with no route gets a 404 and never leaves the host.
  7. ext_authz asks the policy service before forwarding. Envoy sends the method, path, headers, the body (up to 64 KB) and {vm: agent-01, tool: github}. The service checks whether this VM may use this tool, with this method on this repository path, at this size and this rate.
    • If allowed: it gets a short-lived, scoped GitHub token from the credential broker and answers "OK, set Authorization: Bearer …".
    • If irreversible (say, deleting a repository): it answers "denied, pending approval" and queues the request for a human.
    • If not allowed: 403, and the denial is logged.
  8. Envoy resolves api.github.com itself and opens TLS. It verifies the certificate chain and the expected name, then sends the request with the injected token.
  9. The response comes back the same way, and the access log records VM, tool, method, path, status, bytes and duration.

Model inference takes the same path to the proxy on a different route, and the proxy forwards it to the inference VM. The agent never sees a GPU, and the inference VM never sees a credential or the internet.

Glossary

Grouped by layer, from the hardware boundary outward. The indented note under each term says why it matters to this design.

Virtualization

KVM · Kernel-based Virtual Machine
The part of the Linux kernel that uses the CPU's virtualization extensions (Intel VT-x, AMD-V) to run guest code directly on the CPU. When the guest does something privileged, such as touching a device, the CPU leaves the guest (a "VM exit"). KVM handles the exit or passes it to a userspace program.

Here: the boundary the whole design rests on. Nothing in this repo constrains KVM itself.

VMM · Virtual Machine Monitor
That userspace program. It emulates the devices the guest sees. Firecracker, Cloud Hypervisor and QEMU are VMMs.
Firecracker
AWS's VMM, written in Rust, built for Lambda and Fargate. It emulates only a handful of devices: virtio network, block, vsock and balloon, a serial console, and a stub keyboard controller used for reboot. It boots in about 125 ms.

Here: a small device model means little host code the guest can reach.

microVM
A VM with a minimal device model and a minimal kernel, light enough to run one per agent.
virtio and virtio-MMIO
The standard for paravirtual devices. The guest knows it's virtualized and talks through shared-memory ring buffers ("virtqueues") instead of pretending to drive real hardware. virtio-MMIO finds devices at fixed memory addresses with no PCI bus.

Here: that's why the lean kernel can set PCI=n.

jailer
Firecracker's companion launcher. Before starting Firecracker it creates a chroot, new mount and PID namespaces (optionally a network namespace), cgroups, and drops to an unprivileged uid. Firecracker then adds its own per-thread seccomp filters.

Here: if a guest escapes into the VMM, it lands in a jail with no network route.

Cloud Hypervisor, QEMU, Kata Containers
Cloud Hypervisor is a Rust VMM originally from Intel, now a Linux Foundation project. It shares the rust-vmm building blocks with Firecracker but supports PCI and device passthrough. QEMU is the long-established general-purpose VMM, with a much larger attack surface. Kata Containers runs each container pod inside a VM using one of these VMMs; see the Kata section.

Here: the likely VMM for the inference VM until Firecracker's passthrough support ships.

Guest–host channels

vsock · AF_VSOCK
A socket family for host–guest communication. Addresses are (CID, port) pairs, not IP addresses, so there's no routing, no ARP, no DNS and no firewall to configure. The guest needs CONFIG_VSOCKETS and CONFIG_VIRTIO_VSOCKETS. Both sit under the kernel's socket layer (CONFIG_NET), not under TCP/IP (CONFIG_INET).

Here: that's why the guest can drop TCP/IP entirely and still reach the proxy.

CID · Context ID
vsock's address. 0 is the hypervisor, 1 is local, 2 is the host, and 3 and up are guests. vm.json gives the agent CID 3.
Hybrid vsock
Firecracker's version of vsock. On the host side it uses ordinary Unix sockets instead of the kernel's own vsock support (vhost-vsock).
  • Guest connects out to port N: Firecracker connects to <uds_path>_N.
  • Host connects in: it connects to <uds_path> and writes CONNECT N\n, and Firecracker replies OK <port>\n.

Here: the guest can reach only ports for which a _N socket file exists on the host. The set of socket files is the guest's allowlist below HTTP.

UDS · Unix domain socket
A socket at a filesystem path. Access is controlled by file permissions, the listener can read the connecting process's uid (SO_PEERCRED), and it never leaves the machine.
uds_8080
Shorthand for <uds_path>_8080, the host socket file that receives guest connections to port 8080. Envoy binds it as a pipe listener.
MMDS · Microvm Metadata Service
Firecracker's built-in metadata store. The host loads JSON into it through Firecracker's API, and the guest reads it over HTTP at 169.254.169.254 through a virtio network interface; Firecracker answers with its own tiny TCP/HTTP stack. Version 2 requires a session token, like AWS's IMDSv2.

Why it's excluded: every process in the guest can read it, so it's a config channel, not a secret store. It also needs a network card, and this design has none. Configuration goes on the read-only rootfs or comes over vsock instead.

169.254.169.254
The link-local address where cloud providers run their instance metadata service. On a cloud node it hands IAM credentials to anything that can reach it; that was the 2019 Capital One breach, through server-side request forgery.

Here: unreachable, because there's no network card.

kube API
The Kubernetes API server. A mounted service-account token plus a reachable API server lets an attacker act on the cluster without touching the internet.

Here: also unreachable.

Inside the guest

Landlock
A Linux security module that any process, even an unprivileged one, can use to restrict itself, for example "this process may only read /work and write /scratch". Since ABI v4 it can also restrict TCP ports.
seccomp-bpf
A filter on which system calls a process may make, and with which arguments.
Read-only rootfs and scratch drive
The agent can't change its own binaries or persist anything outside a disposable second disk. Firecracker's is_read_only enforces this at the block device, below the guest kernel.
Lean kernel
This repo. Code that isn't compiled in can't be exploited: IO_URING=n, USER_NS=n, BPF_SYSCALL=n, no modules.

Two profiles: the default still builds TCP/IP and the virtio NIC driver, so the optional tap works; with no NIC configured, nothing leaves over IP. VSOCK_ONLY=1 adds configs/vsock-only.fragment, which removes TCP/IP (INET=n), the NIC driver and packet sockets from the kernel.

Proxy

Envoy
The host-side proxy, a CNCF project written in C++. Three parts matter here:
  • Listener: where traffic arrives; here a pipe, meaning a Unix socket.
  • Route: matches path, method and headers to an upstream.
  • Cluster: a named upstream with its own DNS resolution and TLS settings.

Here: the only host process that parses guest input. Jail it, and patch it on the same cadence as the guest kernel.

ext_authz
An Envoy HTTP filter that pauses each request and asks an external service for a decision. Over gRPC the call is envoy.service.auth.v3.Authorization/Check.
  • The request carries the source, method, path, headers, optionally the body, and context_extensions.
  • The answer is either OkHttpResponse, optionally with headers to set or remove (this is how the token gets added), or DeniedHttpResponse with a status code and body.
Open Policy Agent ships an implementation, or you write your own.
context_extensions
Static key-value pairs attached to a route in Envoy's config and passed to the policy service.

Here: they carry the VM and tool identity, which the guest can't forge because Envoy's config sets them.

failure_mode_allow
What Envoy does if the policy service is unreachable. It must be false, so requests fail closed.
SNI · Server Name Indication
The hostname a client sends in plaintext at the start of a TLS handshake. A proxy that can't decrypt traffic can only filter on this.
CONNECT, termination, origination
Three ways a proxy can handle TLS:
  • CONNECT passthrough: the client asks for a raw tunnel and runs TLS through it. The proxy sees only the host name and byte counts.
  • TLS termination: the client's TLS ends at the proxy, which needs a certificate the client trusts. That means planting a CA in the guest.
  • TLS origination: the client speaks plain HTTP to the proxy, and the proxy opens TLS itself.

Here: origination. The proxy sees everything and no CA goes into the guest. Plain HTTP is safe because that leg is a local vsock-to-Unix-socket hop that never touches a network.

netns · network namespace
A separate copy of the network stack: interfaces, routes, firewall.

Here: Envoy runs in one whose only route goes upstream, and Firecracker in one with no route at all.

Credentials

Credential broker
A host-side service that holds long-lived secrets and issues short-lived ones. HashiCorp Vault does this with "dynamic secrets": it mints, for example, a GitHub App installation token or AWS STS credentials with a lease and revokes them when the lease ends.
Short-lived, scoped token
A GitHub App installation token is a concrete example. It expires after 1 hour, is limited to chosen repositories, and carries specific permissions (say, issues: write and nothing else). A leaked one is worth little and soon expires.
Workload identity
The platform tells a service who a workload is, instead of the workload proving it with a stored secret. SPIFFE/SPIRE is the standard toolkit.

Here: the per-VM socket is the identity, so the guest has nothing to steal.

Lethal trifecta
Private data, untrusted content, and a path out. Prompt injection needs all three. The proxy narrows the third.

Limit: hiding the secret stops theft, not misuse. The agent can still use a token's authority through allowed calls, so token scope and per-call policy are the real controls.

GPU

PCIe and BARs
The bus GPUs sit on. Each device has a configuration space and BARs (Base Address Registers, the memory windows the CPU uses to talk to the device). Devices can also do DMA.
DMA · Direct Memory Access
The device reads and writes system memory itself, without the CPU.

The danger: a GPU programmed by the guest could, with nothing in between, DMA anywhere in host memory, including the host kernel.

IOMMU · Intel VT-d, AMD-Vi
An MMU for devices. It translates the addresses a device uses into host physical addresses through per-device page tables. For a passed-through GPU those tables map only the guest's RAM, so DMA elsewhere is blocked. Enabled with intel_iommu=on or amd_iommu=on, now the default on many distros.
Interrupt remapping
Part of VT-d and AMD-Vi. Devices signal interrupts by writing to a special address (MSI). Without remapping, a guest-controlled device can write crafted MSIs and inject arbitrary interrupts into the host, as Wojtczuk and Rutkowska demonstrated in 2011. VFIO refuses to run without it unless you set allow_unsafe_interrupts. Never set it.
IOMMU group
The smallest set of devices the IOMMU can isolate from one another, determined by the PCIe topology. The whole group has to go to one VM. Check /sys/kernel/iommu_groups/.
ACS · Access Control Services
A PCIe feature on switches and root ports that forces device-to-device traffic up to the root complex, where the IOMMU can see it. Without ACS, two devices behind the same switch can DMA to each other directly, around the IOMMU. The "ACS override" kernel patch only pretends ACS exists; don't use it.
VFIO
The Linux framework (vfio-pci, and the newer iommufd) that hands a whole PCI device to userspace safely. The VMM uses it to:
  • map the device's BARs into the guest,
  • program the IOMMU with the guest's memory,
  • route the device's interrupts into the guest through KVM.

Side effect: guest memory has to be pinned, because the device may DMA into any of it at any time. That's why Firecracker's VFIO work preallocates all guest memory, and why memory overcommit and ballooning stop working.

FLR · Function Level Reset
A PCIe feature that resets one device function to its power-on state without resetting the whole bus. The fallbacks are a secondary bus reset or a power-state cycle (D3hot).

Caveats: a reset doesn't guarantee GPU memory is wiped, so scrub it between tenants. It doesn't undo changes to persistent firmware either. If a guest can rewrite the GPU's flash-stored VBIOS, a reset won't clean it.

vGPU, MIG, SR-IOV
Ways to share one GPU. vGPU is NVIDIA's time-sliced sharing, which needs a host-side NVIDIA manager driver. MIG (Multi-Instance GPU) on A100/H100 makes hardware partitions with separate compute and memory slices that still share firmware and a scheduler. SR-IOV presents one physical device as many virtual functions.

Here: avoided across trust domains. One dedicated GPU per trust domain.

virtio-gpu native context, gVisor nvproxy
Both forward the guest's GPU commands or driver calls (ioctls) to the host's GPU driver, putting a large proprietary host driver in the guest's reach. That makes them weaker than passthrough.
Confidential computing
H100s have a "CC mode" that works with AMD SEV-SNP or Intel TDX VMs and encrypts traffic between the VM and the GPU. It protects the model from a compromised host, which is the opposite direction from this design's concern.

Gaps this walkthrough exposes

  1. The relay into the inference VM needs a shim. Opening a connection into a hybrid-vsock guest means writing CONNECT N\n first. Envoy can't send that preamble and doesn't speak AF_VSOCK, so it needs a small relay, or the inference VM opens the connection out to a host listener. Check whether Cloud Hypervisor uses the same Firecracker-compatible protocol.
  2. The guest's TCP/IP stack stays unless tools stop using TCP. The loopback TCP shim needs CONFIG_INET. Tools that open vsock directly, or go through the Unix-socket shim, can run on the vsock-only profile, which has no TCP/IP. Test the agent harness on it before switching.
  3. The socket files are the guest's port allowlist. Create only _8080 for each agent VM, and give each socket permissions that let only that VM's jailer uid connect.
  4. VFIO pins guest memory, so inference VMs can't be packed by overcommitting RAM. Size them for the whole model.

Kata Containers instead of raw Firecracker?

Kata is a container runtime that starts each Kubernetes pod inside its own VM. It plugs into containerd as io.containerd.kata.v2 and is selected with a RuntimeClass. Inside the VM, a small Rust program (kata-agent) receives commands from the host runtime over vsock and starts the containers. The VMM is configurable: QEMU (the default), Cloud Hypervisor, Firecracker, or Dragonball, which is built into the newer Rust runtime.

It's the same isolation class as this design, because a hardware VM boundary and a separate guest kernel come either way. What changes is how much host-side code sits next to that boundary.

Track record. Kata escapes have come through the host-side components that trust guest or pod input, not through KVM:

  • 2020, Unit 42 (Black Hat USA): CVE-2020-2023 let a container reach the guest's root filesystem device and impersonate kata-agent. CVE-2020-2026 let a guest trick kata-runtime into mounting the container image on any host path.
  • 2026, as reported by CVE trackers (confirm against NVD and the Kata advisories): CVE-2026-47243, a guest-root to host-root escape through virtio-fs in runtime-rs, and CVE-2026-44210, a VM escape through virtiofsd argument injection via a default-enabled pod annotation.

Verdict. Kata is a sound replacement for running the microVM layer if the agents land in Kubernetes, but it isn't safer by default. It brings back the egress-pod design from the original reading, and it's the best-maintained GPU path. Configure it down:

  • Use the Firecracker or Cloud Hypervisor VMM, not QEMU, except on GPU nodes.
  • Avoid virtio-fs where you can; with Firecracker, Kata uses block devices (the devmapper snapshotter) instead.
  • Restrict which pod annotations the runtime accepts.
  • Run agent pods on dedicated nodes, and don't mount any Kubernetes credentials.
  • Patch Kata on the same cadence as the kernel.

If the agents don't run on Kubernetes, raw Firecracker with the jailer is the smaller host surface. Keep it.
